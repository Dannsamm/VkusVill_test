# buyer_assistant_test_case

Отчёт описан в REPORT.md

Тестовое задание на роль аналитика качества в команде покупательского ассистента.

## Контекст

В продакшене работает покупательский ассистент ВкусВилла: пользователь описывает свою задачу (что приготовить, что взять с собой, какой собрать набор продуктов), ассистент рекомендует **набор товаров из каталога** и поясняет выбор. Качество ответов мы периодически размечаем руками — это медленно. Хотим заменить (или дополнить) ручную разметку авто-судьёй на LLM.

В репозитории лежит **минимальный рабочий пайплайн** такой авто-разметки, который собрал молодой не опытный аналитик. Он работает, но работает плохо и в среднем дает 30№-40№ точности. Ваша задача — не натренировать классификатор, а восстановить логику разметчиков и сделать LLM-судью, который следует этой логике воспроизводимо.

## Задача

Разберитесь, **почему** пайплайн работает плохо, и улучшите его.

- Нужно провести анализ ошибок судьи: найти типы расхождений с разметчиками, показать примеры и объяснить, какие изменения пайплайна закрывают эти ошибки.
- Можно менять промпт, формат ответа LLM, параметры вызова модели и способ сборки входного контекста для модели.
- Нельзя выносить оценочную логику из LLM в код: итоговая оценка, причины и вердикт должны приниматься на уровне промпта.
- Цель — повысить согласованность авто-разметки с  оценками разметчиков.

В конце сессии расскажите:

- какое качество получилось на доступной вам проверке;
- какие основные причины ошибок вы нашли;
- какие ошибки остались у вашего судьи и почему;
- какие правила идеальных разметчиков вы восстановили;
- что бы делали дальше, если бы было ещё 2 часа.

## Что в репозитории

```text
data/
  labeled_cases.jsonl   — 108 размеченных примеров с причинами решений разметчиков
src/
  pipeline.py           — текущий авто-судья. Читает labeled_cases, сохраняет predictions
  evaluate.py           — считает согласованность с оценками разметчиков
LABELING_GUIDE.md             — инструкция разметчиков
README.md
requirements.txt
.env.example                  — нужен OPENAI_API_KEY
```

Все  оценки разметчиков лежат в `data/labeled_cases.jsonl`. Разметчики ставят `label`, `reason_codes` и `gold_explanation` по инструкции из `LABELING_GUIDE.md`. `label` — целочисленная оценка от `0` до `100`, где `0` означает очень плохой ответ, а `100` — идеально правильный ответ. Это сознательно делает кейс открытым: кандидат может изучать метки и причины, но в итоговом рассказе должен показать, что восстановил процедуру принятия решений, а не просто подогнал ответы под конкретные строки.

Основная метрика в стартовом `evaluate.py` намеренно наивная: точность считается только при полном совпадении числового прогноза с оценкой разметчика. Если авто-судья предсказал `84`, а разметчик поставил `85`, это считается ошибкой.

## Модель

Используется `gpt-4o-mini` через OpenAI API. Менять модель не нужно — задача в инжиниринге пайплайна, а не в подборе модели.
Бюджет: 100 рублей.

Стоимость `gpt-4o-mini` в OpenAI API: $0.15 за 1 млн входных токенов и $0.60 за 1 млн выходных токенов. При курсе 90 ₽/$ это примерно 13.5 ₽ за 1 млн входных токенов и 54 ₽ за 1 млн выходных токенов.

## Формат данных

Одна запись `labeled_cases.jsonl`:

```json
{
  "id": "q_001",
  "question": "что приготовить на ужин для семьи из 4 человек, бюджет 1500",
  "answer": "Текст ответа ассистента с описанием набора...",
  "products": [
    {"id": "vv_001", "title": "Бёдра куриные охлаждённые ВкусВилл", "price": 459, "weight": "1 кг"},
    {"id": "vv_002", "title": "Картофель мытый ВкусВилл", "price": 99, "weight": "1 кг"}
  ],
  "label": 95,
  "reason_codes": ["good_match"],
  "gold_explanation": "Подборка решает запрос пользователя."
}
```

Поля:

- `question` — запрос пользователя;
- `answer` — текстовый ответ ассистента;
- `products` — товары, которые ассистент включил в рекомендованный набор;
- `label` — целочисленная оценка от `0` до `100`;
- `reason_codes` — причины решения разметчика;
- `gold_explanation` — короткое объяснение идеальной оценки.

Ожидаемый формат `outputs/predictions.jsonl`:

```json
{
  "id": "case_001",
  "prediction": 15,
  "reason_codes": ["violates_hard_constraint", "products_contradict_answer"],
  "evidence": ["Пользователь просил без газировки, но в товарах есть газированные напитки."]
}
```

`reason_codes` не обязательны для запуска базового пайплайна, но учитываются при проверке. Решение, которое возвращает только числовую оценку, будет получать неполную оценку по причинам.

## Ограничения на решение

Авто-судья должен возвращать вердикт из самой LLM. Под вердиктом понимается как минимум итоговый `prediction`, а в хорошем решении также `reason_codes` и краткие доказательства решения. Код вокруг модели может готовить вход, вызывать модель, проверять техническую валидность JSON и сохранять результат, но не должен самостоятельно решать, хороший ответ или плохой.

Запрещено применять регулярные выражения, списки ключевых слов, ручную фильтрацию товаров, эвристические правила или постобработку вне LLM для выставления оценки или выбора причин. Например, нельзя в Python искать слова вроде "аллергия", "бюджет", "свинина", "детям" и на основании этого менять `prediction` или `reason_codes`. Если такая проверка нужна, она должна быть сформулирована в промпте и выполнена моделью.
